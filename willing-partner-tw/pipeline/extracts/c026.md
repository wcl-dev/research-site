## Why the Wayback route failed, and how this was actually resolved
The gate record's `collection_note` reported a confirmed Wayback CDX snapshot chain (2021→2026, latest `20260328123925`, HTTP 200) and treated raw-curling that snapshot as the remaining step. **I did that curl — it did not work, and here is the confirmed reason**: `cofacts.tw` is a Next.js app whose `/about` route ships an **empty `__NEXT_DATA__.apolloState: {}`** in its initial HTML. I confirmed this by parsing the embedded JSON directly out of the Wayback snapshot's raw HTML:
```
{"props": {"pageProps": {"apolloState": {}}}, "page": "/about", ...}
```
This means the page's real content loads **client-side via an Apollo GraphQL query after the browser executes JavaScript** — Wayback's (and my) plain HTTP crawl only ever captures the pre-hydration shell. No amount of curling that specific snapshot URL will ever recover the rendered text; this is a structural CSR (client-side-rendered) limitation, not a bot-block. (The snapshot's title tag *did* correctly resolve to "什麼是 Cofacts 真的假的" ("What is Cofacts"), confirming it is genuinely the right page — just empty of body content.)

**Recovery**: since the About page is Cofacts' own open-source frontend (`cofacts/rumors-site`, a public GitHub repo), I located and fetched the actual page component directly: `raw.githubusercontent.com/cofacts/rumors-site/master/pages/about.js` (200 OK). Next.js's file-based routing maps `pages/about.js` → the `/about` route, confirmed by the component's `<title>{t\`What is Cofacts\`}</title>` matching the snapshot's rendered title exactly. This source file **is** the ground truth for what actually displays on the page (via `ttag` i18n template strings — the English literal in the source is the base string that per-locale translations key off of).
